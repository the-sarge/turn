## Goal

Guarantee structurally that a sealed Allocation cannot become the Client's published live Allocation. `UDPConn.Activate(publishAndReleaseAdmission func())` must own one `closeMutex`-held transition that, for a positive initial lifetime, publishes an invariant-complete quiescent `UDPConn` through a narrowly constrained Client callback and then arms all Allocation lifecycle workers before unlocking. `UDPConn` remains the sole owner of activation, maintenance, seal, terminal cause, abort-before-release ordering, exactly one lifecycle-created lifetime-zero Release transaction ID, and caller join.

## Evidence and Supported Domain

At base `12b4233078fa88e6ba54317b57e62e95a5b8e892`, merged product `4a25a8e0b939039f06d6951a88f4571a452f4500`, and investigation head `d3fd19c5cbb040795d61bf80ce0794c792a779ce`, an investigation-only synchronization-based test under `go test -race` constructed a zero-lifetime `UDPConn`, waited for its permanent first Refresh failure to invoke `OnDeallocated`, and then published it. In every tree the callback cleared a still-nil Client pointer, publication installed the already-sealed connection, and the race detector correctly reported no memory race. The defect is lifecycle ordering: the one-shot deallocation notification is consumed before publication, so later admission mistakes a sealed pointer for the live Allocation. The disposable reproducer was not retained; implementation evidence item 2 replaces it with a permanent channel-gated regression test over the production assembly path.

The zero-success characterization replayed base `12b4233078fa88e6ba54317b57e62e95a5b8e892`, merged product `4a25a8e0b939039f06d6951a88f4571a452f4500`, and architecture baseline `d3fd19c5cbb040795d61bf80ce0794c792a779ce` for ten `go test -race` runs apiece. All three showed the same current behavior: the zero-lifetime Allocation was published, later admission returned `ErrAlreadyAllocated`, an ordinary successful zero-lifetime Refresh did not self-seal, and multiple distinct lifetime-zero transaction IDs were created. The observed distinct lifetime-zero transaction ranges were 3–5 at `12b4233078fa88e6ba54317b57e62e95a5b8e892`, 3–5 at `4a25a8e0b939039f06d6951a88f4571a452f4500`, and 3–7 at `d3fd19c5cbb040795d61bf80ce0794c792a779ce`.

That zero-success characterization is distinct from the earlier pre-publication reproduction evidence for the publication-versus-seal race. The later commit `dbfe0b69116ea75f12aae0a64c3943d12df8a2f2` stores the zero-success evidence in `allocation_zero_lifetime_characterization_test.go`; implementation must invert each of its current-behavior assertions into the selected-contract assertion rather than delete the evidence without disposition.

RFC 8656 Section 7.2 floors a newly created Allocation at the 600-second default, but permits a response to a retransmitted Allocate request to carry the Allocation's current remaining lifetime. Section 7.3 requires the client to retain the actual lifetime returned by the server. This client exposes configurable transaction timing, and `internal/proto.Lifetime` decodes the complete unsigned 32-bit seconds representation. The selected product classification is exact: zero denotes terminal server state, while every positive `uint32`-second wire lifetime denotes live state.

For every positive initial lifetime, the refresh cadence remains fixed at initial lifetime divided by two, including a one-second lifetime producing a 500-millisecond cadence. Later positive Refresh grants update the requested lifetime without rescheduling that cadence. Exactly one Release means exactly one lifecycle-created lifetime-zero transaction ID; retransmissions of that ID by the transaction registry are excluded from the count.

The supported domain is the one production `Client.Allocate` assembly path, split by canonical versus invalid relayed address and zero versus positive successfully parsed Allocate lifetime, followed where applicable by activation, ordinary Refresh success carrying a positive or zero lifetime, permanent Refresh failure, caller Close, and later Allocate admission. `internal/proto.Lifetime` owns the wire representation, `UDPConn.Activate` owns activation and the publication boundary, the constrained Client callback owns only pointer publication plus admission-claim release, and `UDPConn` owns terminal lifecycle behavior.

## Decision

`internal/client.NewUDPConn` will return an invariant-complete, quiescent `UDPConn`: all maps, channels, adapters, credentials, timers, and default intervals exist, but no timer goroutine is armed. The existing unexported build-plus-start split is narrowly reopened at the package boundary; the started-constructor behavior accepted by the 2026-08-19 construction plan does not survive as a second production path.

`UDPConn.Activate(publishAndReleaseAdmission func())` will be the sole activation operation. Activation state is protected by `closeMutex`; only the first activation of an unsealed, unactivated positive-lifetime `UDPConn` may invoke the narrowly constrained Client-owned callback and arm timers. It invokes the callback while the Allocation-refresh, permission-refresh, and binding-check timers are all stopped. The callback may only acquire `Client.mutex`, publish the candidate pointer, and release the admission claim. After the callback returns, `Activate` arms all three timers before releasing `closeMutex`. An immediate timer handler may run only after publication, and `startClose` cannot enter its guarded transition until all three timers are armed; sealing then stops all three. Every repeated activation is a no-op that does not invoke the callback or change timer state, whether the connection remains live or has been sealed.

For a successful Allocate exchange with a canonical relayed address and positive initial lifetime, root ordering becomes: construct the quiescent `UDPConn`; canonicalize the relayed transport address; call `Activate` without holding `Client.mutex`; inside `Activate` and while holding `closeMutex`, invoke the constrained callback, which acquires `Client.mutex` only to publish the pointer and release the admission claim; arm all three timers; release `closeMutex`; return the public `Allocation`. This `closeMutex`-then-`Client.mutex` order matches the existing order used when `startCloseLocked` invokes `OnDeallocated`. No caller may acquire `Client.mutex` and then call `Activate`.

If the initial Allocate lifetime is zero, `Activate` does not invoke the publication callback and does not arm any timer. It terminalizes the unpublished `UDPConn` as `ErrAllocationRefreshFailed` wrapping a private turn-prefixed zero-remaining-lifetime cause. `Client.Allocate` returns that error and no `Allocation`, releases the admission claim through the non-publication path, preserves abort-before-release ordering, creates exactly one lifecycle lifetime-zero Release transaction ID, and permits a later `Allocate` to reach the wire. This adds no public error identity: callers receive the existing `ErrAllocationRefreshFailed`, with only its wrapped cause remaining private.

If an ordinary Refresh on an already-published live Allocation succeeds with a zero lifetime, the response is terminal server state and zero is not stored as a live lifetime or used as a timer interval. The Refresh path returns the same private zero-remaining-lifetime cause to `refreshAllocationWithRetries`, performs no stale-nonce retry, and uses the existing worker-safe `startClose` path with `ErrAllocationRefreshFailed`. Structurally, initial zero arms no timer, while an ordinary zero success can arise only after a positive initial lifetime established the existing fixed interval and self-seals before the timer loop can schedule another zero-duration iteration. The terminal transition clears the published pointer, makes operations and caller `Close` expose the terminal cause, creates exactly one lifecycle Release transaction ID, admits a later Allocation, and creates no later distinct Allocation Refresh transaction. This guarantee is limited to the observed zero-lifetime Allocation-refresh defect; existing admission behavior for permission-refresh and binding-check handlers remains unchanged and out of scope.

The observable pre-publication deallocation guard remains rejected. A Client flag, generation handshake, or closed-state check would duplicate `UDPConn` terminal ownership and still require atomic publication-versus-seal arbitration to avoid a check-then-publish race. `Activate(publishAndReleaseAdmission)` removes that state by placing publication and timer activation in the same `closeMutex`-held transition.

**Narrowly reopened decisions:** The construction plan's claim that production needs only a build-plus-start `NewUDPConn` is superseded for this slice. The Allocation lifecycle plan's positive initial RFC-default-grant representation is widened to every positive `uint32`-second lifetime returned by Allocate, while zero is terminal. Its fixed initial half-life cadence, rejection of adaptive refresh, and sole `UDPConn` lifecycle ownership remain binding. The admission plan remains binding: validation precedes activation, and the constrained callback keeps publication plus admission-claim release in one Client-owned critical section.

**Non-goals:** No positive-lifetime clamp or minimum; adaptive refresh; generic timer or clock framework; generic post-close handler-admission gate; constructor options/builder; new public API or public error identity; TURN request or response wire change; retry-policy change except that terminal zero receives no stale-nonce retry; caller-socket close or deadline operation; Client terminality; second admission guard; broad test harness; new permission-refresh or binding-check coverage; unrelated permission, binding, transaction, or packet-path change.

## Implementation Slices

### Slice S1 — Publish within atomic Allocation activation

**What it delivers:** One PR changing `NewUDPConn` to quiescent construction, adding the sole idempotent `UDPConn.Activate(publishAndReleaseAdmission func())` boundary, moving production publication into its constrained callback, classifying zero remaining lifetime as terminal on initial Allocate and ordinary Refresh, updating the complete five-invocation census explicitly, and adding deterministic lifecycle-ordering and positive-cadence evidence without timing sleeps or repetition.

**Single owner after merge:** `newUDPConn`/`NewUDPConn` establish construction invariants; `UDPConn.Activate` alone owns the `closeMutex`-held publication-and-activation transition; its Client-owned callback alone publishes the pointer and releases the admission claim; `startCloseLocked` alone seals, notifies, aborts, and releases in the existing order.

**Authority completeness:** No persisted or restart state exists. The complete five-invocation census is: production `client.go` activates through the publication callback; `close_latency_test.go` explicitly activates; root `scripted_allocation_test.go` explicitly activates; the missing-abort case in `internal/client/udp_conn_test.go` remains a construction panic without activation; and that file's timer test constructs quiescent state and then explicitly activates. No build-plus-start compatibility constructor or additional activation call remains.

**Transitional-seam budget:** None at merge. There is one constructor, one activation method, and one production ordering. No second started constructor, Client-side health flag, sealed-state getter for publication, timer-start hook, clock abstraction, or compatibility wrapper may remain.

**Blast radius:** Concurrency and ordering change only at Allocation activation and terminal zero-lifetime handling. For a positive initial lifetime, timers move from constructor return into `Activate`, the publication callback runs while `closeMutex` is held and all timers are stopped, and all timers are armed before `closeMutex` is released. `Client.Allocate` calls `Activate` without holding `Client.mutex`; the callback alone briefly acquires it in the established `closeMutex`-then-Client-mutex order. Repeated activation of a live or sealed connection is a no-op. Invalid-relayed cleanup closes an unactivated connection. Initial zero never publishes or arms a timer, while a later ordinary zero Refresh self-seals through the existing worker-safe path before another Allocation Refresh iteration can be scheduled. Public API and error identities, emitted bytes, positive fixed intervals, terminal-cause precedence, caller-owned socket behavior, unrelated handler admission, and dependencies do not change. Untraced effects are not accepted: callback work beyond pointer publication and admission-claim release, any timer armed before the callback or left unarmed when `Activate` unlocks, callback reinvocation or timer-state change on repeated activation, any rearm after Close or self-seal, calling `Activate` while already holding `Client.mutex`, a second activation owner, changed abort-before-release order, more than one lifecycle Release transaction ID, changed socket ownership, or any stale-nonce retry for terminal zero stops the slice.
